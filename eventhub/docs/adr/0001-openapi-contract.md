# ADR-001: Використання OpenAPI як єдиного контракту API

## Статус

Прийнято — 2026-10-18

## Контекст

У проєкті EventHub є клієнтська частина на React і серверна частина на NestJS. Для каталогу подій необхідно узгодити структуру даних між клієнтом і сервером.

Без спільного контракту API виникає ризик, що клієнт і сервер використовуватимуть різні назви полів, типи даних або формати відповідей.

На першому етапі лабораторної роботи також необхідно забезпечити тестування клієнта без реалізації повноцінного серверного API.

## Розглянуті варіанти

### Варіант A. Описувати типи вручну

- Плюси: простота початкової реалізації, відсутність додаткових інструментів.
- Мінуси: дублювання типів, можливі розбіжності між клієнтом і сервером, складніше підтримувати зміни.

### Варіант B. Використовувати OpenAPI та генерацію типів

- Плюси: єдиний опис API, автоматична генерація TypeScript-типів, можливість запуску mock-сервера.
- Мінуси: потрібно підтримувати OpenAPI-специфікацію та налаштувати додаткові інструменти.

## Рішення

Використовувати OpenAPI 3.1 як єдине джерело опису контракту API.

Специфікація зберігається у `packages/contracts/openapi/openapi.yaml`.

Для автоматичної генерації TypeScript-типів використовується `openapi-typescript`. Згенеровані типи розміщуються у `packages/contracts/src/api.d.ts`.

Для тестування запитів до `GET /events` без повноцінного бекенду використовується mock-сервер Prism.

Клієнтська частина EventHub отримує події через типізовану функцію `getEvents()`.

## Рішення щодо пагінації каталогу

Для ендпоінта `GET /events` обрано курсорну пагінацію (cursor-based pagination).

Клієнт може передавати параметри:

- `limit` — максимальна кількість подій на сторінці (від 1 до 50, за замовчуванням 20).
- `cursor` — курсор для отримання наступної сторінки.

Відповідь API містить:

- `items` — масив подій поточної сторінки.
- `nextCursor` — курсор наступної сторінки або `null`, якщо наступної сторінки немає.

### Чому обрано курсорну пагінацію

Розглянуто два варіанти:

**Offset-based pagination (`offset` + `limit`):** простіша в реалізації, але під час додавання або видалення подій між запитами можливі пропуски чи дублювання записів.

**Cursor-based pagination (`cursor` + `limit`):** дозволяє стабільніше переходити між сторінками каталогу, якщо порядок сортування визначений однозначно.

Для EventHub обрано курсорну пагінацію, оскільки каталог подій може змінюватися під час перегляду користувачем.

### Компроміси

- Курсор складніше реалізувати на сервері, ніж звичайний `offset`.
- Сервер повинен забезпечити стабільне сортування подій, наприклад за датою початку та унікальним ідентифікатором.
- Курсор не повинен залежати від позиції елемента в масиві.
- На першому етапі лабораторної роботи описано лише контракт пагінації; реальна серверна логіка буде реалізована пізніше.

## Наслідки

**Позитивні**

- Клієнт використовує типи, сформовані зі специфікації API.
- Зменшується ризик розбіжностей у структурах даних.
- Можна тестувати каталог подій без готового серверного API.
- Зміни контракту можна відстежувати у Git.

**Негативні й компроміси**

- Потрібно оновлювати згенеровані типи після зміни специфікації.
- Mock-сервер не замінює повноцінне тестування реального бекенду.
- Для локального тестування потрібно запускати Prism окремо.

**Що доведеться переглянути, якщо...**

Якщо проєкт перейде на інший спосіб опису API або зміниться підхід до взаємодії між клієнтом і сервером, це архітектурне рішення потрібно буде переглянути.
